## Overall recommendation: `converge`

WS0-WP1 behaves correctly as a bounded runtime foundation. Backend and frontend
both come up on their intended ports, the frontend genuinely reads live state
from the backend in the running system, and every not-yet-real aspect is
surfaced honestly (`stubbed-singleton`, integrations `out-of-scope-for-ws0`).
All five required criteria and all four holdout checks passed on observed
behaviour. Two non-blocking nits and two platform-bound caveats are noted. WS0
is sufficient to unlock WS1 planning activation.

### 1. Startup path — PASS (platform caveat)
The intended Pi model is two PM2-managed processes defined in
`sara/runtime/ecosystem.config.js` — `sara-backend` (`backend/server.js`,
`SARA_PORT=4301`) and `sara-frontend` (`vite preview frontend --port 4173`,
`VITE_SARA_API_BASE_URL=http://127.0.0.1:4301`) — registered for boot via
`pm2 save` / `pm2 startup`.

- Ran the exact backend script PM2 invokes: it boots cleanly and logs
  `SARA backend listening on http://0.0.0.0:4301`.
- Built the frontend and ran the same `vite preview` PM2 invokes: it serves on
  `4173` and reports its `0.0.0.0` network URLs (reachable over Tailscale).
- Both bind `0.0.0.0`, matching the documented always-on access model.

**Caveat:** the *auto-start-on-boot* trigger (systemd → PM2 resurrect) cannot be
exercised on this Windows host — no Pi/systemd/PM2 daemon. The substance (clean
bring-up of both processes + survives a stop/start cycle) was runtime-verified;
only the boot hook is asserted from the correct PM2 config rather than executed.
Not a blocker.

### 2. Frontend reachable (always-on mode) — PASS
- `npm --prefix sara run build:frontend` completed (24 modules → `dist/`).
- `GET http://127.0.0.1:4173/` → `200 text/html`, serving the built SPA
  (title "SARA Runtime") with the hashed `assets/index-*.js` / `*.css` references.
- Preview server binds `0.0.0.0` and advertises its LAN/Tailscale URLs.

### 3. Backend reachable on expected runtime path — PASS
- `GET /healthz` → `200` `{"ok":true,"service":"sara-backend","timestamp":...}`.
- `GET /api/runtime` → `200` with `runtime.sharedState` (identity, services,
  display, `nextWorkstreams:["WS1","WS2"]`), `deviceTarget:"Raspberry Pi 5"`, and
  an `integrations` block that explicitly self-reports `out-of-scope-for-ws0`.

### 4. Frontend/backend communication actually works — PASS
- The built bundle issues `GET ${VITE_SARA_API_BASE_URL || http://127.0.0.1:4301}/api/runtime`.
- Reproduced that exact cross-origin request with the frontend's `Origin`
  (`http://127.0.0.1:4173`): backend returned `200`, `Access-Control-Allow-Origin: *`,
  `application/json`. The values the App binds into its status cards/panel were
  pulled live from the backend — `backend=up`, `frontend=expected`,
  `stateEngine=stubbed-singleton`, `deviceTarget=Raspberry Pi 5`, `identity=SARA`.
- The green/connected path is therefore earned from a real round-trip.

**Caveat:** confirmed via reproducing the shipped fetch + bundle inspection plus a
live cross-origin round-trip, not a pixel screenshot — no browser-rendering
harness was available on this host. The DOM paint follows deterministically from
the verified payload and the (inspected) render code.

### 5. Honest failure surfacing — PASS
- **Placeholder honesty:** the runtime payload labels itself as a stub
  (`services.stateEngine:"stubbed-singleton"`, `identity.mode:"ws0-runtime-foundation"`,
  all integrations `out-of-scope-for-ws0`, `services.frontend:"expected"`). The
  slice does not overstate what it is.
- **Down state:** with the backend killed, `GET /api/runtime` is actively
  refused (connection refused) — nothing stale served, no false positive.
- **Failure UI exists:** `App.jsx` wraps the fetch in `try/catch`, throws on
  non-OK, and renders `Backend connectivity failed: <message>` in place of the
  runtime contract. Verified the running app hits this exact path against a dead
  backend (`Backend connectivity failed: fetch failed`). It reports a bad link
  rather than freezing on stale values.

## Holdout checks (mature-runtime risks)

| Holdout | Result |
|---------|--------|
| Restart persistence after stop/start cycle | **PASS** |
| Honest degradation when backend communication fails | **PASS** |
| Empty / placeholder runtime payload handling | **PASS** |
| Configuration dependency failure surfacing | **PASS** (positive path; conflict-crash caveat) |

- **Restart persistence:** killed the backend, restarted it — `/healthz` returned
  `200` again and `/api/runtime` `generatedAt` advanced on each request,
  confirming state is freshly generated per request (no stale caching). Because
  the frontend polls `/api/runtime` every 15s, it auto-recovers to `backend=up`
  once the backend returns. PM2 `autorestart` would perform this recovery
  automatically on the Pi.
- **Honest degradation (key two-process finding):** unlike a single-process
  build, here the frontend (`4173`) and backend (`4301`) are independent
  processes. With the backend killed, the frontend page itself **stayed up**
  (`GET / → 200`) while its API call was refused — so the operator can land on a
  live page whose backend is dead. The app handles exactly this: it renders
  `Backend connectivity failed` rather than a misleading green or a frozen UI.
  Degradation is visible and honest.
- **Empty / placeholder payload handling:** `/api/runtime` returns the stub
  shared-state; the frontend renders its string status values into the cards
  without error, and integrations explicitly render as out-of-scope rather than
  blank. No crash on the intentionally-minimal payload.
- **Config dependency failure surfacing:** `SARA_PORT` override verified live
  (backend served on an alternate port, default `4301` correctly unused).
  `SARA_FRONTEND_ORIGIN` verified live — when set, `Access-Control-Allow-Origin`
  reflects the configured origin rather than the wildcard, so the CORS dependency
  is real and observable.
  **Caveat:** the loud port-conflict crash (`EADDRINUSE`) could not be
  deterministically reproduced on this Windows host — Windows socket semantics
  (`SO_REUSEADDR`) permit rebinding an in-use port, so the fail-fast crash that
  would occur on the Linux Pi target did not fire here. Asserted from standard
  Node behaviour on the target; under PM2 a crash/restart-cap would be
  operator-visible.

## Scoped regressions / nits (non-blocking)

1. **Default-open CORS.** With `SARA_FRONTEND_ORIGIN` unset the backend allows
   `Access-Control-Allow-Origin: *`. The PM2 runtime config does set the explicit
   origin (`http://127.0.0.1:4173`), so the always-on path is scoped — but the
   wildcard default is worth tightening or documenting as a deliberate dev-only
   default. Cosmetic/hardening, not a correctness issue.
2. **No explicit reconnect affordance.** On backend loss the UI shows the error
   text and silently retries every 15s; there is no "reconnecting…" indicator.
   Acceptable for a health surface; a minor UX nicety for a later WP.

No correctness regressions found.

## Sufficiency for WS1 planning activation

**Sufficient.** WS0-WP1 delivers exactly what it claims: a two-process,
PM2-launchable, always-on runtime where a real frontend reads real state from a
real backend over `/api/runtime`, with honest placeholder labelling, honest
backend-down behaviour, and boot-persistence config in place. The state model is
an explicit singleton stub (`stubbed-singleton`, `sharedState` shape with
`nextWorkstreams:["WS1","WS2"]`) — a clean seam for the central State Engine to
replace in WS1, and integrations are explicit placeholders. Nothing observed
blocks WS1 planning activation.

**Recommended (not blocking) before/with WS1:**
- Exercise the systemd → PM2 boot hook once on the actual Pi 5 to close the
  off-platform startup caveat.
- Confirm the `EADDRINUSE` fail-fast behaviour on the Linux target (untestable on
  the Windows eval host) and decide whether a friendly operator message is wanted.
- Tighten or document the default-open CORS posture.
