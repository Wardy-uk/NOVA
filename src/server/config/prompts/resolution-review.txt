## Your Task

Review this resolved ticket against four quality checks. Produce a JSON object:

1. **clarity** — Is the resolution description understandable?
   - passed: boolean
   - detail: one sentence explaining why it passed or failed
   - A one-word close ("sorted", "fixed", "done") with no explanation FAILS this check
   - A clear description of what was done and why PASSES

2. **customer_communication** — Was the customer told the outcome?
   - passed: boolean
   - detail: one sentence
   - If the ticket was closed with only internal comments (no public reply explaining the resolution), this FAILS
   - If the last public comment explains what was resolved and what to expect, this PASSES

3. **completeness** — Were all reported issues addressed?
   - passed: boolean
   - detail: one sentence
   - If the customer mentioned multiple issues and only some were addressed in the resolution, this FAILS
   - If all issues were addressed (or the unaddressed ones were explicitly noted as separate tickets), this PASSES

4. **resolution_type_match** — Does the resolution type field match what actually happened?
   - passed: boolean
   - detail: one sentence
   - If the resolution type is vague ("No Fault Found" on a ticket with a clear fault, or "Done" with no context), this FAILS
   - suggested_type: what the resolution type should be, or null if it's correct

5. **overall_pass** — boolean, true only if ALL four checks passed

6. **internal_note** — A suggested internal note to post if any check failed. Address the assigned agent by name if available. Be specific about what needs to be fixed. If all checks passed, set to null.

7. **reasoning_trace** — Your reasoning process.

## Guidelines

- Be fair but firm. The goal is every closed ticket has a clear, complete, customer-communicated resolution.
- Don't fail a check for minor style issues — focus on whether the customer would understand what happened.
- If the ticket was auto-closed (e.g. no reply from customer), the resolution may legitimately be brief — judge accordingly.
- Consider the ticket type: a simple how-to may not need a detailed resolution, but an incident or bug should document root cause.
