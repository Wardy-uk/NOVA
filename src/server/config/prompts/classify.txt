## Your Task

Classify this resolved ticket:

1. **ticket_type**: ITIL ticket type — one of: incident (unplanned service interruption), service_request (request for help/access/info), change (modification to config/settings), problem (recurring underlying issue)
2. **category**: The broad category (e.g., "Integration", "Portal", "Email", "Reporting", "User Management", "Data", "Performance", "Configuration", "Billing", "Training")
3. **sub_category**: A specific sub-category within the broad category
4. **software_area**: The specific software component or module affected (e.g., "BriefYourMarket Portal", "Dynamics 365 Integration", "Email Templates", "Property Alerts"). Use null if unclear.
5. **problem_type**: One of: bug, config, user-error, data-issue, integration, performance, access, feature-gap, documentation, unknown
6. **root_cause**: A one-sentence description of what caused the issue. Use null if the root cause isn't clear from the ticket.
7. **impact**: How broadly this affected the customer — high (multiple users/business-critical), medium (single user significant), low (minor/cosmetic)
8. **urgency**: How time-sensitive this was — high (SLA risk/blocking), medium (needed soon), low (no time pressure)
9. **priority_matrix**: Derived from impact × urgency — P1 (high+high), P2 (high+med or med+high), P3 (med+med or cross high+low), P4 (remaining low combinations)
10. **confidence**: 0.0-1.0 confidence in the classification
11. **reasoning**: Brief explanation of why you chose this classification

## Rules
- Base classification on the full ticket context including the resolution, not just the initial summary
- If the ticket was resolved as a config change, classify as "config" not "bug"
- If the customer misunderstood a feature, classify as "user-error" not "bug"
- Use specific, consistent category names — don't invent new ones for every ticket
- If confidence is below 0.5, explain why in the reasoning

Respond with valid JSON matching the schema. No markdown fencing.
