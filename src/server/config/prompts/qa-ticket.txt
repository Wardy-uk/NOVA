## Your Task

Score this ticket across multiple quality dimensions:

1. **accuracyScore**: 1-10 — was the diagnosis correct? Was the fix appropriate?
2. **clarityScore**: 1-10 — were responses clear and understandable?
3. **toneScore**: 1-10 — was the tone professional, empathetic, appropriate?
4. **closureScore**: 1-10 — did the agent properly resolve or advance the ticket? Was the resolution communicated clearly?
5. **isConcerning**: true ONLY for a genuine problem a manager needs to act on — a wrong or unsafe fix, rude or dismissive tone, a security or data-protection risk, an ignored customer, or a resolution that plainly did not resolve the issue. Ordinary room for improvement is NOT concerning. A ticket that was handled acceptably is `false` even if it scored 5 or 6. Expect most tickets to be `false`.
6. **severity**: "low", "medium", or "high" — only meaningful if isConcerning is true
7. **category**: The single dimension that most drove the score. Use EXACTLY one of:
   `accuracy`, `clarity`, `tone`, `closure`, `completeness`, `other`. No other values, no free text.

8. **summary**: 1-2 sentence summary of the QA assessment
9. **issues**: Key issues identified in this ticket (1-2 sentences, or empty string if none)
10. **customerSentiment**: "positive", "neutral", or "negative" — the customer's apparent sentiment
11. **firstReplyAssessment**: Score the first agent reply specifically — was it timely, relevant, helpful?
12. **closureAssessment**: Score the closure — was the resolution communicated clearly? Was the customer informed?
13. **issuesFound**: Array of specific quality issues found (empty if none)

Do NOT return an overall score or a grade. Both are derived from your four dimension
scores outside this prompt — anything you supply for them is discarded.

## Resolution Quality Checks

In addition to the QA scores above, assess the resolution against four pass/fail checks.
These are a floor, not a bar for excellence: the question is "would a colleague picking
this ticket up understand what happened?", not "is this the best it could be". Scale the
expectation to the ticket — a password reset needs one clear sentence, an incident needs
root cause. When a check is genuinely borderline, PASS it and explain the reservation in
`detail`.

14. **resolutionChecks.clarity** — Is the resolution clearly documented? Can someone understand what was done?
    - passed: true/false
    - detail: one sentence explaining why it passed or failed
    - A one-word close ("sorted", "fixed", "done") with no explanation FAILS this check
    - A description of what was done PASSES, even if brief — brevity on a simple ticket is not a failure

15. **resolutionChecks.customerCommunication** — Was the customer informed of the resolution?
    - passed: true/false
    - detail: one sentence
    - If the ticket was closed with only internal comments (no public reply explaining the resolution), this FAILS
    - If the last public comment tells the customer what was resolved, this PASSES
    - Auto-closed tickets where the customer stopped replying after being chased PASS

16. **resolutionChecks.completeness** — Were all reported issues addressed?
    - passed: true/false
    - detail: one sentence
    - If the customer mentioned multiple issues and only some were addressed, this FAILS
    - If all issues were addressed (or unaddressed ones were explicitly noted as separate tickets), this PASSES
    - A single-issue ticket that was resolved PASSES

17. **resolutionChecks.resolutionTypeMatch** — Does the Jira resolution type match what actually happened?
    - passed: true/false
    - detail: one sentence
    - If the resolution type contradicts what happened ("No Fault Found" on a ticket with a clear fault), this FAILS
    - A generic-but-not-wrong type ("Done" on a straightforward fix) PASSES — judge accuracy, not expressiveness
    - suggestedType: what the resolution type should be, or null if it's correct

## Scoring Guide
- 9-10: Exemplary — could be used as training material
- 7-8: Good — meets standards with minor room for improvement
- 5-6: Acceptable — gets the job done but notable gaps
- 3-4: Below standard — significant issues that need coaching
- 1-2: Poor — fundamental problems with the interaction

## Calibration
The default for competent, unremarkable work is **7** — a routine ticket diagnosed
correctly and closed with a clear reply to the customer is 7-8, not 5-6. Reserve 5-6 for
work with a real gap a customer or colleague would notice. Do not deduct for what is
merely absent when it was not needed. Score each dimension independently — a weak closure
must not drag down the accuracy or tone score.

## Rules
- Score based on what actually happened, not what you'd have done differently
- If the ticket was resolved quickly and correctly, that matters more than perfect prose
- A simple fix done well deserves a good score — don't penalise simplicity
- Flag concerning behaviour only for genuine issues (rude tone, wrong fix, security risk)
- If the ticket was resolved by an automated process, score the process appropriately
- For resolution checks: be fair but firm. Don't fail for minor style issues — focus on whether the customer would understand what happened
- If the ticket was auto-closed (e.g. no reply from customer), the resolution may legitimately be brief — judge accordingly
- Consider the ticket type: a simple how-to may not need a detailed resolution, but an incident or bug should document root cause
